# Milestone 1 corrective delivery and acceptance status

The four authorized sibling targets contain the reusable DAV, Graph and contacts packages and independent Linux BusyCards implementation. This corrective delivery fixes the Microsoft claims handshake, RFC 6578 limit-error handling and version-specific vCard parameter grammar. Google synchronization was checked against its current primary endpoint contract: the endpoint specifies consistent request parameters and requires the sync flag to return a replacement token, so the working rotation flag is retained with separate initial/incremental regressions.

**Full Milestone 1 acceptance remains open.** The machine denies loopback TCP and Unix sockets, preventing the standard Flutter driver, interactive MSAL callbacks, independent DBus/X11 execution and positive Secret Service acceptance. Live provider resources/registrations remain unauthorized. Eleven BusyFiles generated-file differences also appeared against this corrective task's starting snapshot; attribution is unresolved and nothing was reverted. Existing applications have no new package dependencies or integration. **Milestone 2 has not started.**

## Implemented application and package paths

The original architecture and workflows remain in production paths: ordinary pure Dart protocol/domain packages, generated People client, distinct CardDAV/CalDAV APIs and typed provider semantics. BusyCards binds Google, Microsoft and CardDAV/Nextcloud with its own registration inputs, Settings-based account/source management, cached search/list/details/editor, safe common/provider edits, photos/organization, durable drafts and pending/conflict reconciliation, bounded vCard import preview/export and per-item bulk results. Widgets use shared account-scoped mutations. Google groups, Microsoft folders/categories and CardDAV address books are distinct. The private SQLCipher store persists complete provider source records and searchable projections transactionally with cursors/journals; OS credential protection has no plaintext fallback or shared donor store.

Microsoft contacts PATCH lacks an established atomic If-Match endpoint guarantee: changeKey preflight detects some changes but cannot eliminate the intervening lost-update race. Work/school JPEG contact-photo writes use documented permissions and a 2 MiB client cap; personal-account photo writes and undocumented deletion remain unsupported. The Google and Microsoft app-owned registrations are configurable, not borrowed or fabricated. All other BusyStack applications may be absent. The copied BusyMax native architecture remains one HdyApplicationWindow, one engine/FlView, Flutter header/sidebar and Yaru/GTK service adaptation; no new desktop design was introduced. Exact rendered parity remains unverified.
